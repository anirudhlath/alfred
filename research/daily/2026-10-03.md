# Daily Note — 2026-10-03

## Memory-decay eval (EXP-006)

First runs of `python -m evals memory run` (60 simulated days, seed 7,
`google/embeddinggemma-300m` on CPU, Redis 8.2.10 in a throwaway container). Rows in
`data/memory-decay.csv`; analysis in `experiments/EXP-006-memory-decay.md`.

**Events processed per policy:** 13,316 memories written (12,839 routine, 434 reflex,
30 significant, 5 recalled, 8 detail), 72 simulated retrievals, 1,440 decay passes,
33 probes at days 30/45/60. 26,632 write-path embeddings.

**Decay pass latency (ms):**

| policy | p50 | p95 | p99 | max | embeds | migrated |
|---|---|---|---|---|---|---|
| no_decay | 50 | 57 | 145 | 192 | 1,440 | 0 |
| branch | 48 | 123 | 184 | 378 | 1,788 | 166 |
| oracle | 711 | 2,189 | 2,817 | 3,840 | 24,614 | 9,585 |

**Token usage:** none (no LLM; compression uses the Librarian's concatenation
fallback).

**Anomalies:**
- The branch's decay pass sees ≤19 candidates (`FT.SEARCH` without `LIMIT`).
- The cold store's `vec0` tables use L2 distance; `1 − distance` is reported as a
  cosine-scale score, so `EpisodicMemory.recall` buries every cold result.
- The unfiltered hot KNN query (`memory_recall_memories`) misses 73–90% of targets an
  exact search puts in the top 10, and its results differ between two runs with the
  same seed.

## Memory decay after the fixes (EXP-007)

All seven EXP-006 problems fixed on the PR #247 branch, then the same 60-day run
(seed 7, EmbeddingGemma on CPU, Redis 8.2.10): run `2026-10-04T032859`, rows in
`data/memory-decay.csv`; analysis in `experiments/EXP-007-memory-decay-fixed.md`.
An earlier post-fix run, `2026-10-04T025923`, is in the CSV too; it predates the
compression-grouping fix and differs only in the oracle's archive.

**Events processed per policy:** unchanged — 13,316 memories, 72 retrievals, 1,440
decay passes, 33 probes, 26,632 write-path embeddings.

**Decay pass latency (ms):**

| policy | p50 | p95 | p99 | max | embeds | migrated |
|---|---|---|---|---|---|---|
| no_decay | 0 | 0 | 0 | 1 | 0 | 0 |
| branch | 418 | 888 | 1,273 | 1,689 | 5,440 | 9,585 |
| oracle | 327 | 739 | 970 | 1,279 | 5,440 | 9,585 |

At threshold 1.0 `decay_candidate_ranges()` returns nothing, so `no_decay` makes no
query.

**Token usage:** none.

**Results:** the branch now equals the oracle on every recorded field; involuntary
hit@10 76% → 67% at day 60 under both (one-off details retired by design); the tool
finds 5/8 departed targets (EXP-006: 0/8) and 28/33 overall under every policy
(EXP-006: 3–6/33).

**Anomalies:**
- Two defects found while fixing: a "database is locked" race on the cold store's
  first open (WAL switch), and compression grouping that depended on candidate order.
  Both fixed.
- One search miss per policy remains at day 60: a 236-way tie on a shared semantic
  key (no_decay) and a hot target at rank 10 displaced by a cold result in the
  tool's merge (branch, oracle).
